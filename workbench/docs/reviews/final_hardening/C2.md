## Checklist answers (the three mandatory questions)

**(1) Is the evidence-ledger append HMAC-authenticated with a key stored outside the artifacts tree, so a
filesystem attacker cannot forge corroboration?**
*Verdict: VARIANT.* The append is genuinely HMAC-SHA256 per entry with a chain (`evaluate_models.py:1196-1201`,
`1233`, `1278`) and the key is resolved outside the artifacts tree, preferring `WORKBENCH_LEDGER_KEY` then
`$XDG_CONFIG_HOME/cir/workbench_ledger_key` (`evaluate_models.py:1110-1147`). **But** (a) the ledger file
itself is inside the artifacts tree (`evaluate_models.py:1091-1096`:
`WORKBENCH_ARTIFACTS_ROOT/evidence_ledger.jsonl`), i.e. the same writable tree as the reports, and (b) the
fallback key location is computed from `HOME`, which the production allowlist **does** forward to the
untrusted official evaluator child (`evaluate_models.py:438`). In the documented zero-configuration
deployment that lets model code read the signing key and mint a fully authenticated forged corroboration;
reproduced end-to-end below (F-01, P1). With `WORKBENCH_LEDGER_KEY` supplied from outside and the legacy
repo-root key absent, the forgery path is closed. So: HMAC = YES; "keyed outside artifacts" = YES;
"a filesystem attacker cannot forge" = **NO in the default deployment, YES only when the operator sets the
key externally.**

**(2) Does C-5's demotion make full pass impossible for any legitimate committed row (all 28 rows publish
category tables — verify)?**
*Verdict: NO — the demotion cannot fire on any committed row, and no committed row is blocked by it.*

lacks `category_metrics`** (`python` + `yaml.safe_load` over `papers.yaml`; all 28 carry exactly
`dress/shirt/toptee` with numeric `r10`/`r50`, no `None`). `paper_gate.py:432` therefore never executes for
committed data. Counterfactual check of the new rule in isolation (mapping forced `verified=True` so the
unrelated mapping rule cannot mask it; run values = reference comparison values, all category cells exact):
**27/28 rows reach `PASS_WITHIN_5_PERCENT`**; the single exception is `limn_fashioniq_base_iter0_table1`
(`BLOCKED_CHECKPOINT_MISMATCH`) and that is the *pre-existing* bundle-id rule (`paper_gate.py:367-377`
compares `checkpoint_id` against the reference's `base_iter0_all_categories`), not C-5. Passing the real
plan's bundle id — which is what a LIMN run actually records (`evaluate_models.py:238`, `:368-382`;
`adapters/models.py:137`) — the same row yields `PASS_WITHIN_5_PERCENT passed=True`. So: honest rule, no
false happy-path casualty. Over-restriction note in F-05 (P3).

**(3) Does the conesep id fix actually unblock gate selection end-to-end?**
*Verdict: VERIFIED for gate selection; VARIANT for "unblock the journey".* `papers.yaml:647/695/743` now
name `fiq_n02/fiq_n05/fiq_n08`; the registry declares exactly those three

## Findings

### F-01 — P1 — the untrusted evaluator child can forge a fully authenticated ledger entry (CONFIRMED)
*Claim (attack on the C-4 fix):* `/api/*` corroboration is only as strong as the ledger key, and in the
documented zero-configuration deployment the child that must never forge entries can read that key.
*Evidence (reproduced, `/tmp/c2f2`):* the child environment was built by the production
`_evaluator_environment` (`evaluate_models.py:467-494`) — its only relevant entries were
`['CIR_REPO_ROOT', 'HOME']` (observed print) — and a subprocess with exactly that environment:
1. read `$HOME/.config/cir/workbench_ledger_key` (the documented fallback, created by the operator's own
   first call — observed `fallback key file: True len 32`),
2. wrote `reports/model_ckpt_RUNY_aggregate.json` with
   `benchmark_gate: {status: PASS_WITHIN_5_PERCENT, passed: True, reference_evidence: {reference_id: fabricated}}`,
3. computed `hmac.new(key_derived_from_env, canonical_record, sha256)` and appended the entry.
Result: `CHILD forged: model_ckpt_RUNY_aggregate.json` / `served: [('RUNY', True)]`.
A second variant with `WORKBENCH_ARTIFACTS_ROOT` also passed in gave `backend serves forged row:
[('RUNX','model',True)]`. The child had NO `WORKBENCH_LEDGER_KEY` in either case.
*Root cause:* `ledger_hmac_key` (`evaluate_models.py:1124-1147`) prefers a repo-root legacy file and otherwise
creates the key under `$HOME/.config/cir/`; `HOME` is on `_EVALUATOR_ENV_ALLOWLIST` (`evaluate_models.py:438`)
because model scripts need it; the child can also reproduce the artifacts path
(`artifact_root`, `evaluate_models.py:1304-1311`, uses `CIR_REPO_ROOT`, also allowlisted).
*Contradicts:* an existing first-wave statement quoted in `C.md:411-416` treats the repo-root legacy key as
the only weak point and calls the private `$XDG_CONFIG_HOME` fallback "the good state"; the repo-root path is
in fact *unreachable from the child* (`/repo/.workbench_ledger_key` does not exist in the image:
`docker run ... ls -la /repo/.workbench_ledger_key` → `No such file or directory`), while the `$HOME`
fallback *is* reachable.
*Recommended action (minimal):* the ledger key must never be derivable from the evaluator child's
environment. Either (a) stop forwarding `HOME` to the official evaluator (`_EVALUATOR_ENV_ALLOWLIST`,
`evaluate_models.py:438`, replacing it with a private `TMPDIR`/`HOME` under the run directory — the CLI
already gives the child a private `TMPDIR`), or (b) fail closed on the fallback key in the API path and
require an explicit `WORKBENCH_LEDGER_KEY`. (a) is one line and removes the whole class.

### F-02 — P1 — ledger corroboration does not bind the report's identity: two files for one run are both served (CONFIRMED)
*Claim (attack on the C-4 fix):* the corroboration tuple checks `report_digest` + three identity fields
against *some* ledger entry with a matching `run_id` (`main.py:149-160`), but nothing enforces one file per
run, and the ledger's own duplicate-run-id refusal never sees a second file.
*Evidence (reproduced, `/tmp/c2h`):* a legitimate run `r1` had its evidence file in `reports/`; a second file
`zzz_forged_aggregate.json` holding byte-identical evidence was then placed beside it. Observed:
`served count: 3 [('r1','a'), ('r9','a'), ('r1','a')]` and `gate keys: ['r1','r9']`. The duplicate passes
`_aggregate_report_is_well_formed` (`main.py:169-180`), finds the witness by `run_id`, matches the digest, and
is appended — `/api/benchmark-runs` returns two rows for one run. A copy whose *content* still names the
original run is likewise served under whatever `run_id` the duplicated bytes carry (`/tmp/c2r`:
`served rows: [('A','m'), ('A','m')]`).
*Impact:* the endpoint lists phantom/duplicated runs; a copied report inherits another run's corroboration;
the "one evidence file per run" invariant that `run_report.open("x")` enforces at write time
(`evaluate_models.py:1509-1512`) is not enforced at read time.
*Recommended action:* in `_aggregate_reports`, require the file name to match the canonical
`{model_id}_{checkpoint_id}_{run_id}_aggregate.json` shape for the report's own fields and skip a `run_id`
already served in this scan.

### F-03 — P1 — corroboration ignores `return_code`/`invocation_status`, so a failed run's report is served as a pass (CONFIRMED)
*Evidence (reproduced, `/tmp/c2rc`):* a ledger entry with `return_code: 1`,
`invocation_status: INVOCATION_FAILED`, `execution_status: EXECUTION_FAILED` and a matching `report_digest`
for a report claiming `passed: True` → `served despite ledger return_code=1: [('RC', True)]`.
*Root cause:* `main.py:153-160` compares digest and three identity fields only. Contrast the canonical
consumer `autopilot.py:730-731`, which rejects `witness.get("return_code") not in (0, None)` and
`autopilot.py:743`, which rejects a non-`EXECUTION_COMPLETED` report. The API lost the second half of
that contract while gaining the first.
*Recommended action:* add `witness.get("return_code") in (0, None)` and
`report.get("execution_status") == "EXECUTION_COMPLETED"` to the corroboration predicate (two conditions,
same place).

### F-04 — P1 — unverifiable ledger ⇒ total evidence outage in the shipped container deployment (CONFIRMED)
*Evidence (reproduced):* with the shipped compose stack (`docker-compose.yml:31` `user: 1000:1000`) the
container is non-root with `HOME=/` (`docker run --rm --user 1000:1000 ... id; echo HOME=$HOME` →
`uid=1000 gid=1000`, `HOME=/`, `config_home= /.config`, `no passwd entry for 1000`), `mkdir /` is refused
(`root NOT writable`), `ledger_hmac_key` → `LedgerKeyError cannot read or create the evidence ledger key`,
`read_evidence_ledger` → `None`, and `_aggregate_reports()` skips **every** report:
`served: []` — including the report that the same artifacts root serves fine on the host
(`host backend with key: ['R1']`). Grep for the key in the deployment surface returns nothing:
`grep -rn "LEDGER" workbench/docker/*.sh workbench/docker/.env.example` → no matches.
*Root cause:* `main.py:137` treats `read_evidence_ledger(...) is None` as "no entries" rather than "cannot
verify"; `read_evidence_ledger` (`evaluate_models.py:1289-1302`) returns `None` both for a missing ledger and
for an unusable key. Combined with F-01's fallback path this is also the *only* realistic deployment, so the
verdict is: the fix works, the deployment cannot use it.
*Recommended action:* one condition — when the ledger *file exists* but `read_evidence_ledger` returns `None`,
log an operator error and treat corroboration as failed with a distinct reason; plus pass
`WORKBENCH_LEDGER_KEY` in the compose/env-file surface.

### F-05 — P2 — the gate cannot certify a run against a reference that prints only an average, even with full observed coverage (CONFIRMED, over-restriction)
*Evidence (in-process):* a reference with `reported_metrics` matching and no `category_metrics`, a run whose
three category rows are exact, and a fully stated run meta → `PASS_WITH_UNCHECKED_CATEGORIES passed=False`
(`paper_gate.py:432-439`). Before the fix the same inputs could return an unqualified pass; now the status
is honest but the direction is opposite and symmetric: a *future* row that prints only `Avg.` (the
`conesep_fiq_n00`/`airknow_fiq_*pct` rows have `checkpoint_id: None` and print tables, but nothing in the
schema forces a table) can never certify a run whose per-category coverage is complete and agreeing.
*Assessment:* not a release blocker (all committed rows publish tables — verified in question (2)), but it is
the mirror image of the reported C-5 hole and it will silently demote a legitimate future row.
*Recommended action:* demote only when the *observed* coverage is smaller than the coverage the run's own
protocol declares; when the run observed all three categories, the per-category check was performed and the
paper row's silence is a reference-provenance fact for `detail`, not a pass-blocking condition. (The
first-wave recommendation in `C.md` C2 is the same: source the completeness floor from the run.)

### F-06 — P2 — the reference and the registry disagree about the conesep checkpoint mapping, and the gate certifies the optimistic one (CONFIRMED)
*Evidence:* `papers.yaml:648` (`conesep_fiq_n20`) says `checkpoint_mapping_status: UNVERIFIED`;
`models.yaml:196` (`fiq_n02`) says `checkpoint_mapping_status: VERIFIED_METADATA`; the plan's

`checkpoint_mapping_status` (`(ver.reference_evidence or {}).get("checkpoint_mapping_status")` → `None`;
`BenchmarkReference.as_evidence` `benchmark_references.py:91-108` does not include it).
*Impact:* the strongest verdict the gate can emit is issued for the rows whose paper→asset identity the
first-wave audit explicitly could not establish (C1's "no author hash" list includes `conesep fiq_n02/n05/n08`).
*Recommended action:* include the reference's `checkpoint_mapping_status` in `as_evidence`, and refuse (or
label) a verdict whose identity signal is stronger than the reference's own recorded state.

### F-07 — P2 — the documented limn reports-dir guard is bypassable through a symlinked parent (CONFIRMED)
*Evidence (reproduced with `preflight`/`evaluate_categories` stubbed so the guard is the only code under
test):* `--output /tmp/c2g/reports/x.json` → `[BLOCKED] --output must not target the official reports
directory`, rc 1; `--output /tmp/c2g/alias/x.json` where `alias -> reports` → `[OK] result written`, rc 0,
and `written through the alias: True` while `resolved name: reports`.
*Root cause:* `limn.py:238` compares `args.output.parent.name` textually.
*Impact:* low — the file cannot pass the aggregate parser (observed `served: []` for a
`limn_base_iter0_dress_*_aggregate.json` dropped into a reports dir), because it carries no
`artifact_type: official_aggregate_evaluation_report` (`main.py:145-146`). So this is defence-in-depth only:
the guard is not the load-bearing control for the diagnostic-does-not-get-served property.
*Recommended action:* `args.output.parent.resolve().name == "reports"`, or better, have the flag check the
same `reports_root` the backend serves from.

### F-08 — P3 — `data_kind="synthetic"` yields `NOT_RUN` with a misleading reason, and autopilot still reports `COMPLETED` (CONFIRMED)

## Verdict

**BLOCKED** — the C-4 fix is real but incomplete in three ways that are all reproducible from the worktree,
one of them reintroducing the exact class of false pass the fix was written to close:

- **F-01 (P1)** — in the documented zero-configuration deployment the untrusted official evaluator can read
  the ledger key out of its own `HOME` and mint a fully HMAC-authenticated forged corroboration; observed
  serving of a forged `passed=True` row from the child environment alone.
- **F-02 (P1)** — corroboration keys on `run_id` and digest but not on file identity: two files for one run
  are both served, and a copied report inherits another run's corroboration.
- **F-03 (P1)** — corroboration ignores the ledger's `return_code`/`invocation_status` that the autopilot
  consumer does check, so a failed run's `passed=True` report is served.
- **F-04 (P1)** — the shipped non-root container cannot create or read the ledger key, so the new guard turns
  the whole `/api/benchmark-runs` + `/api/runs/gate` surface into an empty list; the fix is unusable where it
  ships.

Clean: C-3 (conesep ids) is fixed and verified end-to-end; C-2 (synthetic `data_kind`) refuses correctly; C-5
cannot fire on any committed row and no legitimate row loses a full pass (27/28 in isolation, +1 for LIMN's
bundle id); `RunMetadata.runtime_adaptation` and every other schema/serialization touch in the slice hold.

Should-fix, not blocking: F-05 (inverse over-restriction for a future average-only row), F-06 (conesep
mapping-state disagreement certified optimistically), F-07 (limn guard bypassable, defence-in-depth only),
F-08 (`NOT_RUN` reason text / autopilot `COMPLETED`), F-09 (missing cross-file checkpoint-id assertion),
F-11 (disk-full suite attempt; targeted suites green).
