## 2. `user: "${WORKBENCH_UID:-1000}:${WORKBENCH_GID:-1000}"` bricks the deployment (ROOT_CAUSE A-03). **P1 — NEW P0 REGRESSION**

**Verdict:** BLOCKED. **Severity:** P1 (regression, not in any first-wave report). **CONFIRMED.**

Trace: `docker-compose.yml:22` sets `user: 1000:1000`; `docker-compose.yml:35-36` mount
`${HOST_WORKBENCH_ARTIFACTS_ROOT}:/artifacts` (i.e. the repo's `workbench/artifacts`, owned
`heheboiz:heheboiz` = 1000:1000, mode 0775) and `${HOST_WORKBENCH_CHECKPOINTS_ROOT}:/checkpoints`
(= `workbench/artifacts/checkpoints`). `Dockerfile` has no `USER` and no `HOME`/`MAMBA_ROOT_PREFIX`.
`python:3.13-slim-bookworm` leaves `HOME` unset, so the kernel falls back to `/`
(`docker run --rm --user 1000:1000 --entrypoint sh docker-workbench -c 'echo HOME=$HOME'` → `HOME=/`).

Boot consequence — the real entrypoint dies (RUNTIME_VERIFIED, `docker run` of the production CMD,
image not modified):

```
$ docker run --rm --user 1000:1000 --entrypoint sh docker-workbench \
    -c 'timeout 25 python workbench/scripts/serve_workbench.py --production-frontend --host 0.0.0.0'
...
    code: 'EACCES',
    path: '/repo/workbench/frontend/node_modules/.vite-temp/vite.config.mts.timestamp-….mjs'
[WARN] npm exited with status 1
serve_workbench rc=1
```

The same probe as root succeeds. `serve_workbench.py:175-178` returns the child's exit status, so the
container's PID 1 exits; compose `restart: unless-stopped` (`docker-compose.yml:8`, empty
`user:` seen live) turns this into a crash loop. **No stack boots with the default 1000:1000.**

Why it worked before: the live container runs as **root** (`docker exec cir-workbench id` →
`uid=0(root) gid=0(root)`, `docker inspect … user=` empty, image predates the edit), which is why
`npm run preview` works today and why A-03's original repro passed.

Supply-chain consequence — `prepare` cannot install the model environment (RUNTIME_VERIFIED):

```
$ docker run --rm --user 1000:1000 -e HOME=/ --entrypoint sh docker-workbench -c \
   'micromamba create --prefix /tmp/mb-test --dry-run -c conda-forge --override-channels python=3.11'
Fetch Shard Index for conda-forge/linux-64
critical libmamba filesystem error: cannot create directories: Permission denied [cache]
# and in micromamba info:  package cache : /.local/share/mamba/pkgs
```
With a writable root prefix the exact same call succeeds:
`-e MAMBA_ROOT_PREFIX=/artifacts/mamba -e HOME=/artifacts` → `Total download: 46MB … Dry run. Not
executing the transaction.` `MAMBA_ROOT_PREFIX` appears nowhere in the repository
(`grep -rn MAMBA_ROOT_PREFIX .` → no match). So under the default uid, `install --allow-env-install`
fails at the solver while the planner's allowlist explicitly forwards `HOME` unmodified
(`environment_planner.py:44`).

Training-data consequence — every `user_cache` auxiliary destination resolves under `/`
(RUNTIME_VERIFIED against the real registry):

```
$ .venv/bin/python … auxiliary_destination(asset, /third_party, /data/FashionIQ)   # HOME=/
  /.cache/torch/hub/checkpoints/resnet50-19c8e357.pth
  /.cache/clip/RN50x4.pt
  /.cache/lavis/blip2_pretrained.pth
  /.cache/torch/hub/checkpoints/eva_vit_g.pth
  /.cache/huggingface/hub/models--bert-base-uncased/vocab.txt
```
and those roots are unwritable by uid 1000:
```
$ docker run --rm --user 1000:1000 --entrypoint python docker-workbench -c 'Path("/.cache/clip").mkdir(parents=True)'
mkdir FAIL  /.cache/clip PermissionError [Errno 13] Permission denied: '/.cache'
```
The same is true for `/.local/share/mamba/pkgs`. The *reasonable* first fix — invoking the stack with
`WORKBENCH_UID=$(id -u) WORKBENCH_GID=$(id -g)`, exactly as `.env.example:41-44` advises — resolves to
1000:1000 and inherits every failure above.

Partial mitigation, still insufficient: `data/fashionIQ_dataset` and `workbench/third_party` are
mode 0775 owned by uid 1000, so `/data/FashionIQ`, `/third_party`, `/artifacts` and `/artifacts/results`
are writable by uid 1000 (RUNTIME_VERIFIED). But `workbench/artifacts/checkpoints` contains
root-owned children from previous root-era runs
(`-rw-r--r-- root root workbench/artifacts/checkpoints/download_manifest.json`,
`drwxr-xr-x root root workbench/artifacts/checkpoints/limn`), so existing installs cannot be
repaired by the new uid without a `chown`. Measured ownership histograms:
`artifacts {0: 25588, 1000: 1694}`, `data/fashionIQ_dataset/resized_image {0: 15540}`.

**Recommended action (one place, not a new mechanism):** make the container self-consistent instead
of only dropping privileges from compose —
* set `USER`/`user` to a value that is meaningful in the image and in the bind mounts, or keep the
  `user:` and make the container's writable roots follow the process: `HOME`, `MAMBA_ROOT_PREFIX`,
  `XDG_CACHE_HOME`/`TORCH_HOME`/`HF_HOME` pointed at the writable `/artifacts` mount in the Dockerfile
  `ENV` (and `chown` `/repo` to the container uid at build), and
* `chown -R` the pre-existing root-owned trees under `workbench/artifacts/**` and
  `data/fashionIQ_dataset/resized_image` on the host, or document the one-time `chown`.
Either way the change MUST be validated by starting the real stack as the compose uid and letting
`serve_workbench.py` stay up — the current edit has never been exercised that way.
This is the same root cause as the A-03 finding it claims to fix: uid 0 was clamped at the process
identity, not at the writable roots.

## 3. M1/M2 mutating `run.sh` in place + crash-restore path cannot work (ROOT_CAUSE A-09). **P2**

**Verdict:** BLOCKED (subset). **Severity:** P2. **CONFIRMED.**

(a) The mutations are real and detectable — I reproduced both off-repo
(`/tmp/a2/mut`, fake `docker` on PATH, deterministic stub on :8977; no repo file touched):

```
unmutated:                 model=limn checkpoint=base_iter0_all_categories protocol=fashioniq_val_split
M1 (stdin discarded):      malformed JSON from api/models: Expecting value: line 1 column 1 (char 0)
M2 (bundle preference off): model=limn checkpoint=base_iter0_dress      protocol=fashioniq_val_split
```
This confirms the A-09 claim that M1/M2 now detect real mutants (`mutation_checks.sh:93-118`).

(b) **Constraint violated:** `mutation_checks.sh:93`/`:107` `backup()` then writes the mutant into
`${HERE}/run.sh` (line 49-57 `mutate()`), runs it (line 96/110), and only restores at line 104/116 or
via the EXIT trap (`:19-24`). A `SIGKILL`/power loss between those points leaves the release
launcher mutated in the working tree, and `mutate` uses `${REPO}/.venv/bin/python` (`:49`), which does
not exist in the container the script documents itself for.

(c) **The crash-recovery that is supposed to repair (b) cannot work.** `mutation_checks.sh:32-37`:
```
original="${saved##*/}"; original="${original//_/\/}"
cp "${saved}" "${REPO}/${original}"
```
The backup name is the **full path with `/`→`_`** (`backup()`, `:43`), so the filename is
`home_heheboiz_data_cir_workbench_docker_run.sh`; `##*/` is a no-op (no `/` remains) and the `_`→`/`
substitution is therefore applied to the entire absolute path. RUNTIME_VERIFIED on a throwaway tree
mirroring the real paths:
```
cp: cannot create regular file '/tmp/a2/restore/repo//tmp/a2/restore/repo/workbench/docker/run.sh': No such file or directory
restore rc=1
```
Held-back backups are **reached but never restored** — the recovery silently no-ops, and on a crash
the launcher stays mutated. The "startup restore below repairs a tree left mid-mutation" comment
(`:30-31`) is not true.

**Recommended action:** back up with a flat basename keyed by an explicit path map (e.g. store a
`path<TAB>sha` manifest next to the copies) instead of deriving the path from the filename; and make
the mutation run from a copy of the repo tree (or at minimum refuse to run when `run.sh` is not the
git-clean version) so a crash can never leave a mutated release artifact.

## 8. Queue recovery persists but does not survive a restart into the API. **P2 — scope clarification of A-05/D-5**

**Verdict:** CONFIRMED. **Severity:** P2 (matrix overclaims).

RUNTIME_VERIFIED with the production code, off-repo (`/tmp/a2/cq2`, `SingleGpuQueue` + `recover_interrupted`):
```
after enqueue:            queue_state.json exists = False (dir does not exist yet)
after worker starts:      queue_command.json, queue_state.json, queue_stderr.log, queue_stdout.log
rolling status:           running
final status:             completed
recovered:                [('ca2f29f3-…', 'failed', 'workbench restarted while the job was in flight')]
on-disk after recovery:   failed
RAM after recovery (what /api/jobs serves): []
```
So: `_persist` (`jobs.py:245-263`) is a best-effort snapshot that correctly skips a not-yet-created
directory; `recover_interrupted` (`jobs.py:266-291`) does rewrite `running`→`failed`, is idempotent
(`test_final_hardening_regressions.py:147-165`), and cannot misfire on a different artifacts root
because it only ever touches paths under the passed root and no-ops when the root is absent
(`:274-276`). But the recovery is a **file rollback, not state restoration**: after boot
`GET /api/jobs` (`main.py:331-333`) returns the fresh `SingleGpuQueue`'s RAM list, which is empty.
The reconciled records sit on disk in `WORKBENCH_ARTIFACTS_ROOT/queue_jobs/<id>/queue_state.json`
and have no reader in the backend (`grep -rn queue_state.json workbench/backend` → only `jobs.py`).
Consequences: the escaped-job case (so slow that `recover_interrupted` flips its record to `failed`
while the child still runs) is invisible to the operator; the D-4 duplicate guard
(`main.py:370-376`) is blind to a pre-restart job still holding the GPU; and the ROOT_CAUSE_MATRIX
phrasing "restart lost jobs and left `running` phantoms … FIXED" is not earned — the phantom is
repaired only in the JSON document, and the job list is still lost.

**Action (pick the smallest of):** either load `queue_jobs/*/queue_state.json` into the queue's RAM
list at startup so `/api/jobs` reports the recovered records, or state the limitation explicitly
(records are audit-only after a restart) and drop the "jobs are recovered" claim from the matrix.

## Final verdict

**BLOCKED** — name the findings:

1. **Finding 2 (P1, CONFIRMED):** the new `user:` mapping (`docker-compose.yml:22`) breaks the
   deployment. With the default 1000:1000 the real entrypoint exits 1 before serving (vite cannot
   write `/repo/workbench/frontend/node_modules/.vite-temp`, `HOME=/` is read-only), `micromamba`
   cannot create its cache and every `user_cache` auxiliary destination resolves to the unwritable
   `/.cache/**`; existing installs additionally hold root-owned files under
   `workbench/artifacts/checkpoints`. The edit that claims to fix A-03 was never exercised under the
   uid it sets, and clamping the process identity alone is the same root cause.
2. **Finding 3 (P2, CONFIRMED):** `mutation_checks.sh` mutates the release launcher in place and its
   crash-recovery path cannot restore it; the crash story in the matrix is not implemented.
3. **Finding 7 (P2, CONFIRMED):** `/api/models` is too slow for J1/J4's 60 s probes on the real
   registry, the live paths are skipped (`000`), and J4 passes offline against a stub that re-implements
   the pipeline; J4(b) is a source-grep the M2 mutant defeats.

The first-wave P1s themselves are genuinely fixed: `.dockerignore` `**/.env` is CONFIRMED to exclude
the real file with negative and positive controls (1), the queue recovery is real and idempotent (8),
J11 no longer touches the production container, J4/acceptance-B/C scanners are real, and the verifier
verdict no longer claims `RELEASE_READY` on a non-GPU host. Nothing in the fix wave is fabricated —
but the new `user:` edit is a **new** P0-class regression in the deployment surface, so the slice is
not releasable until finding 2 is fixed and re-verified by actually booting the stack as the compose
uid.
