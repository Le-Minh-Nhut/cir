  evaluation, so `/api/benchmark-runs` and `/api/runs/gate` now serve nothing for genuine runs —
  strictly worse than HEAD, which at least served genuine (and forged) reports.
- **Evidence**:
  - `main.py:168`: `and witness.get("invocation_status") == "EXECUTION_OK"`.
  - The only producer of `invocation_status` is `workbench/scripts/evaluate_models.py:1417-1419`:
    `("INVOCATION_FAILED" if code != 0 else "INVOCATION_COMPLETED" if produced_output else "INVOCATION_NO_OBSERVABLE_OUTPUT")`,
    written into the ledger at `evaluate_models.py:1528`.
  - Repo-wide `grep -rn "EXECUTION_OK"` (excluding `.git`, `.venv`, `__pycache__`) → exactly two hits:
    `workbench/backend/main.py:168` and the test fixture `workbench/tests/test_http_api_layer.py:135`.
    The string appears nowhere else in the repo, in the registry, or in the docs.
  - Reproduced end-to-end with the real producer (STATIC_AUDIT + RUNTIME_VERIFIED in-process, real HMAC
    key + real ledger file):
    `em.append_evidence_entry(cfg, {... "invocation_status": "INVOCATION_COMPLETED", "report_digest": em.sha256_file(p)})`
    → `ledger invocation_status written by the real producer: INVOCATION_COMPLETED`;
    `report_digest matches file: True`; `main._aggregate_reports()` →
    `workbench: skipping aggregate report /tmp/d2f/art/reports/limn_b_aggregate.json: disagrees with its evidence-ledger entry`
    → `reports served by _aggregate_reports(): 0`.

    report (`HEAD _aggregate_reports served: 1 report(s)`), so the fix both refuses forgeries and, as

  and `GateDetail` degrade to silence).

- **Action**: `invocation_status` in the ledger is the *invocation* status; compare it against
  `"INVOCATION_COMPLETED"` (evaluate_models.py:1417), or drop that conjunct and keep `return_code == 0`

## 2. P1 — `queue_state.json` is written only when the log directory already exists ⇒ crash recovery (A-05/D-5) does not cover the states it claims

- **Claim**: "snapshots on every transition" is false for `queued`; the ROOT_CAUSE_MATRIX claim
  (`queue_state.json` snapshots on every transition + `recover_interrupted()` at startup) is overstated.
- **Evidence**:
  - `jobs.py:104` calls `self._persist(job)` in `enqueue`, but `_persist` (`jobs.py:245-262`) writes only
    `if directory.is_dir()`, and the worker creates the directory later (`jobs.py:302`,
    `directory.mkdir(parents=True, exist_ok=False)`). `main.py:400` hands `enqueue` a
    `queue_jobs/<uuid4().hex>` path that does not exist yet.
  - RUNTIME_VERIFIED in-process: `q.enqueue(...)` → `enqueued status: queued logdir exists: False`,
    `state file present after enqueue: False`.
  - Cancelling a still-`queued` job is never persisted at all: `cancel` (`jobs.py:124-128`) sets
    `job.status = "cancelled"` and returns **without** any `_persist` call (the fix added `_persist` only
    at jobs.py:104/157/316/347/378/386). Observed: `A: cancel queued -> cancelled`,
    `A: dir exists: False | state file exists: False`. So a queued job cancelled before dispatch leaves
    **no** record the status API or recovery can see.
  - `preparing` is persisted (`jobs.py:157`) but only after the directory exists, so a process death
    between `enqueue` and `mkdir` (queue backlog, restart, etc.) leaves no record: `recover_interrupted`
    iterates `root.glob("*/queue_state.json")` (`jobs.py:277`) and silently skips such jobs.
- **Severity: P1** (the D-5/A-05 recovery claim; an operator reading
  `/api/jobs` after a restart cannot see the lost job at all, and the docs say otherwise).
- **CONFIRMED.**
- **Action**: make the job directory in `enqueue` (`mkdir(parents=True, exist_ok=True)`) before
  `_persist`, and call `_persist` in both `cancel` branches. One test: enqueue → kill the worker before
  dispatch → `recover_interrupted` must report the job.
