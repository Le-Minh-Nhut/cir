### B2-5 — P2 — the adaptation gate is unsound for adaptation values other than `sm_<n>`, and `torch_arch_list=None` reads as "matches"
- **Evidence**: `runtime.py:1900-1911`:
  ```
  target = adaptation_target.replace("sm_", "").replace("_blackwell", "")
  arch_list = [str(a).lower() for a in result.get("torch_arch_list") or []]
  device_cap = str(result.get("compute_capability") or "").replace(".", "")
  if target not in arch_list: capability = False; ...
  elif device_cap and device_cap != target: capability = False; ...
  ```
  The registry declares the target as a *compute capability* (`models.yaml:948`
  `target_compute_capability: sm_120`), so the normalization is internal to this function and the
  current value works. But for any declaration not shaped `sm_<digits>[_blackwell]` the arch-list test
  degenerates (`target not in arch_list` is trivially true, so `capability` is silently set `False`
  with a confusing `adaptation_mismatch`); and when `device_cap` is empty (`GPU_PROBE_CODE` leaves
  `compute_capability` `None` for an override record), the `elif` short-circuits, so a record with
  `torch_arch_list` containing the target and *no* probed capability is accepted. Observed live: one
  on-disk capability record has `torch_cuda_version='11.7'`, `compute_capability=None`,
  `torch_arch_list=None`, `probe_source='override'` — i.e. the shape the code cannot reason about.
- **Status**: CONFIRMED by source + one on-disk record; not executed against a fake probe in-process.
- **Action**: read the target as `int(major)*10+minor` once, at the registry parse boundary
  (`_adapted_packages` already owns that role), and require `device_cap or <explicit unknown>` rather
  than `device_cap and ...`.

## 4. Verdict

**VARIANT.**

The `cuda: '11.7'` declaration is **real evidence, not invented** — reproduced from the pinned PyPI
wheel's own `torch/version.py`, and the `_requires_gpu` gate it enables now genuinely blocks CSMCIR
