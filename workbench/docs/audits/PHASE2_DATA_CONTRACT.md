## Workbench coverage vocabulary

- **CAPTURED**: workbench preparation/evaluation contract represents the source requirement and its relevant semantics.
- **PARTIAL**: workbench represents some paths or semantics but omits a source-required detail, transformation, provenance, or constructor prerequisite.
- **MISSING**: no corresponding workbench contract/policy represents the requirement.
- Status order in final column: **layout / gallery / auxiliary assets / captions / images / fresh constructor**. Paths after each status name the workbench file(s) that would need updating to close that gap. These labels describe contract coverage, not successful preparation or reproduced model behavior.

Common workbench baseline: `workbench/backend/fashioniq_layout.py:CATEGORIES` lists `dress`, `shirt`, `toptee`; `standard_paths`, `ilearn_resized_paths`, `ilearn_resized_training_paths`, and `dcnet_paths` check directory/file presence, not image membership/content. `workbench/scripts/prepare_dataset.py:required_layout` always selects standard layout, and `validate_fashioniq` checks only that result. `workbench/scripts/prepare_model.py:status` uses preparation registry paths only when `preparation_contract_for_model` finds a contract; otherwise it falls back to `standard_paths`. The shared dataset parser/formatter is `src/datasets/fashioniq.py:load_fashioniq_annotations`, `load_fashioniq_split_ids`, `normalize_fashioniq_caption`, and `compose_fashioniq_caption`; it does not open images or implement source tokenizers/image transforms. The three workbench cohort definitions are in `workbench/registry/models.yaml:protocols`; the evaluator distinguishes reference-eligible recall from reference-excluded recall in `src/evaluation/fashioniq.py:evaluate_fashioniq_recall`.

### Coverage notes across rows

- Gallery assignments above are source-native validation behavior. Workbench `workbench/registry/models.yaml:protocols` assigns registry IDs; `src/evaluation/fashioniq.py:build_original_gallery`, `build_val_gallery`, and `build_fashioniq_gallery` build full-split/endpoint-union galleries, while `evaluate_fashioniq_recall` selects reference-eligible vs reference-excluded metrics. There is no `conf/protocol/*.yaml` file to maintain. Before the alias correction, the generic evaluator accepted internal names `fashioniq_original` and `fashioniq_val` only, so registry IDs `fashioniq_original_split` and `fashioniq_val_split` were unbuildable; `build_fashioniq_gallery` now accepts both spellings. `fashioniq_full_gallery_ref_excluded` is unchanged and already matched its registry ID.
- `src/datasets/fashioniq.py:normalize_fashioniq_caption` reproduces the first-stage iLearn lowercase/punctuation/dictionary rule if the identical dictionary is supplied; it does **not** represent LAVIS postprocessing, model tokenizer limits, CLVC markers/vocabulary, DCNet vector PKLs, or TG-CIR's external tokenizer. A matching composed string alone does not establish model-input parity.
- `workbench/registry/preparation_contracts.yaml` has method-specific records for CLVC-Net, DCNet, CLIP4Cir, TG-CIR, SPRC, and LIMN only. The iLearn model entries generally name `manual_ilearn_resized` but have no method-specific `preparation_id`; see `workbench/registry/models.yaml` and `workbench/backend/registry.py:preparation_contract_for_model`. This makes their `prepare_model.py:status` fall back to standard paths, even where runtime `fashioniq_layout.py:ilearn_resized_paths` knows the validation directories. `prepare_dataset.py:required_layout` is standard-only for all methods.
- Asset provenance gaps are not filled by similarly named files in another checkout. In particular, correction dictionaries for Air-Know, ConeSep, HABIT, HINT, INTENT, ENCODER, and PAIR have no provenance in their pinned trees or workbench asset registry. CSMCIR's Qwen files have a pinned HF revision but no file digest; COT files have no pinned source at all. TGCIR and LIMN correction dictionary files exist in their pinned trees. DCNet/CLVC ResNet weights have only a hash prefix in the preparation contract; CLIP4Cir base RN50x4 has a full registered hash.

## Laptop-testable versus GPU-host requirements

**Laptop-testable now from source/config alone:** exact path joins, trailing-separator requirements, filenames, categories, validation-file/cache branches, gallery construction/reference rules, caption string transforms, declared tokenizer limits, preprocessing operation order, and whether a resize cache is assumed. Evidence is the source functions cited per row plus `fashioniq_layout.py`, the registries, and the evaluator. No actual FashionIQ dataset files, checkpoint bytes, or host package stack were inspected here, so existence, contents, hashes, source-specific importability, tokenizer outputs, and pixel equivalence are **not** confirmed. With local data/dependencies present, a laptop can check required paths/file extensions, hash data/assets, compare annotation/gallery IDs and sample composed captions, and execute CPU image transforms against fixture images; no GPU is needed for those contract checks.

**Requires the configured GPU host for end-to-end model evaluation:** loading each method's exact published weights/base weights in its source-compatible environment, native model inference, category Recall@K, and comparison with reported results. GPU-host work is only actionable after required checkpoints and a runnable source path exist. Air-Know, ConeSep, HABIT, HINT, INTENT, CLVC-Net, PAIR, and TG-CIR do not have a verified workbench evaluation command/checkpoint route in the pinned-source audits; ENCODER has a missing imported module; SPRC's CLI model default/checkpoint mapping is unresolved; those are **blocked before GPU evaluation**, not “GPU-tested.” DCNet and LIMN have implemented workbench replay paths but still need verified runtime/data/checkpoint prerequisites and GPU-host evaluation. CLIP4Cir has a source validator/adapter path but needs the fixed source-root dataset staged and checkpoint mapping resolved. CSMCIR has a source validator path, but its PNG-vs-registered-standard-image layout and unverified auxiliary requirements must be resolved first.
